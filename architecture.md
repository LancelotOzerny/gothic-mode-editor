# Gothic Editor — архитектура

Gothic Editor — настольный редактор модов для **Gothic 2: Ночь Ворона**, написанный на **Python / Tkinter**. Все конечные категории предметов имеют JSON-формы свойств.

## Где что находится

`compile.ps1` в корне собирает Windows-приложение в `dist/GothicEditor.exe`
через уже установленный PyInstaller (`--onefile --windowed`), включая всё `assets/`.
Если в корне есть `icon.ico`, она используется как иконка EXE. Скрипт работает
из любой текущей папки, выбирает активное/локальное виртуальное окружение или
Python из PATH; параметр `-Python` позволяет указать интерпретатор явно.
Перед упаковкой проверяется доступность Tcl/Tk; PyInstaller запускается с
`--clean`, чтобы старый кэш не исключил интерфейс или изменённые модули из EXE.
Пакеты автоматически не устанавливаются. Служебные файлы помещаются в
`build/pyinstaller/`, ошибка сборки возвращает код 1. Параметры упаковки описаны
в [документации PyInstaller](https://pyinstaller.org/en/stable/usage.html).

## Разделение интерфейса

`ui/widgets/panel.py` содержит общий `Panel` и `ScrollableArea`: растягиваемый
контейнер Canvas с автоматически подстраиваемой шириной содержимого и общим
`RoundedScrollbar`. `attach_scrollbar` подключает тот же scrollbar к консоли,
списку ресурсов и другим нативным спискам. Колесо над дочерними элементами
прокручивает только область под курсором; привязки снимаются при уничтожении.
Иерархия, свойства, консоль и ресурсы остаются в прежних `PanedWindow`/`BottomDock`,
с сохранением разделителей, минимальных размеров и растяжения.

`ui/widgets/form.py` задаёт `create_field` для текста, чисел, выбора и переключателей,
а также `FormGroup`. Свойства и настройки используют одну фабрику и одни группы.
Контейнер предоставляет `panel.add_group(title)`; группа —
`group.add_field(title, kind='text', ...)` и `group.add_button(text, command)`.
Настройки сохраняют свои Tk-переменные и запись по кнопке «Сохранить», свойства —
свой контроллер, черновики и автосохранение после паузы во вводе. Фабрика не записывает данные.

`PropertyEntry` и `NumberField` сохраняют нативный ввод/выделение Tk Entry;
общие Ctrl+C/X/A/V работают и при русской раскладке Windows по физическим
кодам клавиш. В readonly разрешено копирование, изменения блокируются.
`make_entry` теперь создаёт тот же `PropertyEntry`, включая поиск и диалоги.
Числовое поле допускает редактирование/вставку и шаг кнопками или стрелками,
а окончательную проверку значения выполняет существующий контроллер настроек.

`ui/windows/dialog.py` содержит общий `EditorDialog`: оформление кнопок,
центрирование и явно выбираемая модальность. Настройки, создание проекта,
добавление предмета и подтверждения сохраняют свой модальный режим;
окно выбора значения остаётся без захвата мыши. Повторяющаяся ручная прокрутка
и стандартные поля настроек заменены общими компонентами.

Просмотр модели использует `core/mesh.py` (геометрия, UV и материалы 3DS/MRM),
`mesh_materials.py` (встроенный бинарный архив материалов MRM), `textures.py`
(TGA и ZTEX, включая DXT1–5) и `model_preview.py` (загрузка ресурсов в фоне).
Каталог `ArchiveModels.texture_entries` хранит ссылки на текстуры VDF отдельно
от моделей; архивы не распаковываются целиком. Сначала ищутся ресурсы предмета,
папка исходной модели, `Assets` проекта и `_work/data/Textures` игры, затем VDF
с прежним приоритетом проекта и дат архивов. Имена сравниваются без учёта регистра.
`core/preview_render.py` рисует UV-текстуры с буфером глубины стандартными средствами
Python в отдельном процессе; `ui/controllers/preview_renderer.py` управляет одним
заданием и последним актуальным запросом, не накапливая очередь движений мыши.
`core/preview_worker.py` хранит сцену в процессе: геометрия и текстуры передаются
один раз на версию модели, последующие задания содержат только параметры камеры.
`ModelViewer` создаёт Tk PhotoImage в UI-потоке и хранит до четырёх готовых кадров;
неизменившийся вид берётся из кэша. Результаты старой модели отбрасываются,
во время расчёта сохраняется предыдущий кадр. Ожидание результата не блокирует Tk.
При уничтожении просмотрщика завершаются задания и принадлежащий ему процесс;
`freeze_support()` в `main.py` поддерживает запуск из собранного Windows EXE. Неподвижная
модель рисуется в разрешении области просмотра, без растягивания
уменьшенного кадра; текстуры используют билинейную фильтрацию с учётом альфы.
Для уменьшения текстур выбирается mip-уровень по UV-производным треугольника:
усреднённые копии готовятся один раз в фоновом загрузчике и хранятся у `Texture`.
Это подавляет рябь мелкого рисунка при уменьшении. Растеризация обходит только
отрезок внутри треугольника в каждой строке, веса вычисляются приращениями.
Повторные запросы от мыши и изменения размера объединяются до перерисовки;
после серии событий колеса полное качество восстанавливается с задержкой 120 мс.
При вращении разрешение временно ограничивается, после отпускания мыши
восстанавливается полное качество. Режим без текстур показывает обводку
видимых полигонов с проверкой глубины и освещение по нормалям граней. По умолчанию
включён режим без текстур; одна toggle-кнопка справа сверху включает/выключает текстуры.
Вторая кнопка фиксирует ракурс инвентаря для предметов; в режиме мира/NPC она отключена.
Иконки: `assets/icons/viewer_textured.png`, `assets/icons/viewer_inventory.png`;
при отсутствии используются текстовые обозначения. При недоступной текстуре
соответствующие грани показываются серыми, а панель сообщает количество пропусков.
Модель изначально вписывается целиком в область просмотра. Экспорт геометрии,
импорт ресурсов и сборка не используют эти настройки просмотра и не изменены.
Форматы сверены с исходниками [ZenKit](https://github.com/GothicKit/ZenKit/tree/main/src).

`core/inventory_preview.py` задаёт базовые углы категорий и применение
`inv_rotx`/`inv_roty`/`inv_rotz` по
[OpenGothic InventoryRenderer](https://github.com/Try/OpenGothic/blob/master/common/graphics/inventoryrenderer.cpp).
Углы в градусах редактируются в общем `general/appearance.json`, сохраняются
обычным механизмом предметов и экспортируются в Daedalus. Отсутствующие значения
не дописываются автоматически; числовые выражения и целочисленные константы
вычисляются без исполнения Python/Daedalus. Неизвестное выражение показывает ошибку.
Фиксация строит отдельную копию геометрии для просмотра, не меняя файл модели,
UV или материалы. Вращение и масштабирование мышью блокируются; при выходе
восстанавливается свободная камера. Изменение углов обновляет фиксированный вид.
При загрузке предпросмотра исходная 3DS преобразуется из Z-up в Y-up Gothic
перестановкой Y/Z; уже скомпилированная MRM повторно не преобразуется. Читатель
геометрии и экспорт исходных байтов не меняются. Инвентарные повороты применяются
в порядке матрицы `Rx * Rz * Ry`, затем меняются выходные оси X/Z и направление
экранной Y/глубины. Перестановка входных осей до вращения неверна: она меняет
назначение `inv_rot*` и кладёт пользовательские зелья набок. Регрессионные проверки
охватывают базисные оси, смешанный поворот, вертикальную MRM и Z-up 3DS с `inv_roty=45`.
Это предпросмотр ориентации: ортографическая проекция, автоматическое вписывание
и освещение редактора не воспроизводят пиксельно рендер Gothic; `inv_animate`
не проигрывается и `inv_zbias` не влияет на масштаб этого предпросмотра.

## Объекты мира

В верхнем поле «Режим» доступны «Предметы», «Мир», «NPC» и «Рецепты»; кнопок переключения над
иерархией предметов нет. Режимы используют существующие растягиваемые панели
и общий просмотрщик. В режиме «Мир» показываются объекты, NPC имеют отдельный режим.
Основные списки показывают только добавленное в проект; «Добавить из Gothic»
открывает отдельный каталог оригиналов с поиском. `core/project_selection.py`
сохраняет членство в `Assets/Worlds/catalog.json` и `Assets/NPC/catalog.json`.
Геометрия копируется только при замене; ранее назначенные замены автоматически
считаются проектными. Метаданные каталогов не упаковываются в MOD.
«Удалить из проекта» с подтверждением убирает запись из каталога и сбрасывает
замену модели мира либо свойства NPC. Несохранённый черновик удалённого NPC
и таймер автосохранения отменяются. Общие импортированные модели NPC остаются
в библиотеке; глобальные текстуры мира сбрасываются отдельно, поскольку их
могут использовать другие объекты. Ресурс можно вновь добавить из Gothic.
«Объекты» показывают статические модели
3DS/MRM из исходников и VDF игры, исключая известные модели предметов. Каталог
строится при первом открытии раздела и обновлении ресурсов; геометрия читается
только при выборе объекта. Поиск скрывает пустые категории. Группировка
«Архитектура», «Растительность», «Мебель», «Декорации» приблизительная, по имени
и пути ресурса; это каталог ресурсов, а не список размещённых Vob конкретной ZEN.
Редактирование геометрии локаций и размещения объектов не реализовано.

Открывающиеся сундуки — объекты мира, а не `C_Item`. Каталог мебели также
включает ресурсы `CHEST*.MDL`/`CHEST*.MDM` из анимационных архивов и loose-файлов.
Для одинакового имени выбирается MDL, иначе MDM с соответствующей MDH.
Составная геометрия и крышка собираются существующим читателем родных моделей
с учётом иерархии. Доступны предпросмотр исходной позы, текстуры и экспорт 3DS;
статической 3DS/MRM анимированный сундук заменить нельзя, кнопка отключена.
Подпись «Сундук» обеспечивает русский поиск. Для добавления используется
«Мир → Добавить из Gothic»; в списке предметов инвентаря контейнеры не появляются.

`WorldResources` сохраняет разрешённые замены в `Assets/Worlds/overrides.json`
(версия 1, `resources` с ключами `model:<имя>` / `texture:<имя>`). Модель находится
в `Assets/Models/World/<исходное имя>.3ds`, текстура — в
`Assets/Textures/World/<исходное имя>.tga`. Для готовой MRM используется
`Assets/Models/World/<исходное имя>.mrm` и `format: "mrm"` в записи замены.
MRM включается в `_work/data/Meshes/_compiled/` с исходным игровым именем;
при установке и запуске сбрасывается соответствующий loose-кэш с резервной копией.
Если заменяемый ресурс уже имеет MRM в VDF, исходной 3DS недостаточно:
сборка останавливается с требованием готовой MRM. Компилятора 3DS → MRM
в редакторе пока нет. Это предотвращает ложную успешную сборку, при которой
игра продолжала использовать оригинальную MRM (например, книжный шкаф).
Имена, типы, категории и пути
проверяются; абсолютные пути/выход за Assets/ссылки не допускаются. До записи
проверяется формат, при ошибке сохранения метаданных прежний файл восстанавливается.
Отмена удаляет только запись замены и её проектный файл. Оригиналы игры не меняются.

В свойствах доступны экспорт, замена и отмена замены модели, список назначенных
текстур, их просмотр/экспорт/замена/отмена. Изменение глобального ресурса требует
подтверждения: оно действует на все объекты с таким именем. Загрузка использует
общие `ModelPreviewCache` и фоновый загрузчик; переключение разделов отменяет
устаревший результат и сохраняет черновик предмета. Экспорт MRM в 3DS через
`model_export.preview_3ds` сохраняет UV-швы и назначенные текстуры, в рамках лимита
65535 вершин/граней 3DS. Анимации и другие данные прогрессивной модели не экспортируются.

`ModelLibrary` не переименовывает и не упаковывает файлы замен мира как модели
предметов. Старый библиотечный `World/model.3ds` остаётся поддержанным. Репозиторий
подставляет активные замены в индекс моделей; предпросмотр учитывает глобальные
замены текстур, сохраняя приоритет локальных текстур библиотечных моделей.

`BuildAssetService` включает только зарегистрированные замены с исходными
игровыми именами и обнаруживает конфликты с прочими ресурсами проекта. JSON
замен не включается в MOD. Для моделей проверяются текстуры проекта и игры,
включая VDF. Для текстуры упаковываются TGA и `<имя>-C.TEX`: `textures.write_ztex`
пишет BGRA без потерь с mip-уровнями от меньшего к большему, по формату
[ZenKit Texture.cc](https://github.com/GothicKit/ZenKit/blob/main/src/Texture.cc).
Это позволяет заменить уже скомпилированную игровую текстуру. Исходные файлы
игры не изменяются; для заменённых 3DS действует существующий сброс кэша геометрии
при установке/запуске мода.

### NPC

`core/npcs.py` читает наследование `INSTANCE`/`PROTOTYPE` до `C_NPC`, имена,
вызовы `B_SetNpcVisual`/`Mdl_SetVisual`/`Mdl_SetVisualBody` и обычные void-функции
без аргументов, задающие внешность существ. Проектные скрипты имеют приоритет.
Произвольный Daedalus не исполняется; неизвестные способы задания внешности
не подменяются предположениями, но имя NPC можно изменить независимо.

`NpcStore` хранит только отличия имени, скелета, тела, головы и брони в
`Assets/NPC/overrides.json`. `ui/controllers/npc.py` сохраняет после паузы
в 1000 мс; Ctrl+S и переход между NPC/режимами, обновление, сборка и закрытие
сохраняют оставшийся ввод. Отмена изменений возвращает исходные назначения.
Список NPC и панель свойств используют общие поиск, поля и тёмные группы.
Имена и назначения меняются у выбранного NPC, общие игровые функции не правятся.

`core/npc_models.py` собирает статическую исходную позу тела и головы. MDM
содержит вложенные прогрессивные меши, MMB — меш головы и исходные позиции
морфинга; MDH задаёт положение головы и жёстких вложений. Учитываются root
translation, назначенная броня (`visual_change` предмета), варианты текстур
тела, лица и зубов. Модели и текстуры загружаются в фоне и используют общий
кэш предпросмотра. Проигрывание анимаций, морфинг и симуляция NPC не реализованы.
Форматы сверены с [ModelMesh.cc](https://github.com/GothicKit/ZenKit/blob/main/src/ModelMesh.cc),
[ModelHierarchy.cc](https://github.com/GothicKit/ZenKit/blob/main/src/ModelHierarchy.cc)
и [MorphMesh.cc](https://github.com/GothicKit/ZenKit/blob/main/src/MorphMesh.cc).
`VdfArchive`/`ArchiveModels.animation_entries` индексируют ресурсы NPC отдельно
от статических моделей предметов и объектов мира.

Для тела выбирается родная MDM, для головы — MMB; импорт создаёт общую
проектную модель с уникальным `GE_NPC_…` в `Assets/NPC/Models/`, не заменяя
оригинальную модель остальных персонажей. Нужен совместимый скелет; броня
перекрывает назначение тела, поэтому доступен отдельный выбор брони/«Нет».
Упаковка включает модели в `_work/data/Anims/_compiled/` под их проектными
именами, JSON редактора в MOD не входит.

`ProjectTools._prepare` после обычного объединения скриптов вызывает
`apply_npc_overrides`: в сборочной копии дописывает имя и/или назначения
внешности в конец нужного `INSTANCE`. Неизвестные поля, AI, расписания,
соседние NPC, функции и исходная кодировка сохраняются. Отсутствующий NPC
останавливает сборку с указанием файла метаданных. Исходники Gothic не меняются.

## Предпросмотр и ресурсы предметов

`ModelPreviewCache` хранит до восьми загруженных моделей. Ключ учитывает источник,
размер и время изменения файла, проект, ревизию ресурсов и режим просмотра;
для текстурного режима также учитывается папка ресурсов предмета. В режиме без
текстур загрузчик читает только геометрию и материалы, не сканирует папки текстур
и не декодирует изображения. Готовые кадры сохраняются при переключении предметов
и повторно используются для той же модели, камеры, размера и режима. Полное
обновление проекта инвалидирует кэш ресурсов. Изменения внешних ресурсов можно
подхватить командой обновления проекта.

Импорт модели, предпросмотр и упаковка используют общий `texture_names.texture_candidates`:
имя материала без расширения также сопоставляется с `.tga`, `.tex` и `-C.TEX`,
с учётом регистра и без следования путям, записанным внутри модели. При упаковке
`BuildAssetService` исправляет ссылки материалов в байтовой копии 3DS для MOD:
например, UUID без расширения превращается в имя найденной TGA; для `NAME-C.TEX`
используется логическая ссылка `NAME.TGA`. Размеры вложенных блоков пересчитываются,
геометрия и UV сохраняются. Исходная модель и ресурсы проекта не перезаписываются.
Это действует и для ранее импортированных ресурсов; повторный импорт не нужен.
Отсутствующие текстуры и конфликты имён по-прежнему останавливают упаковку.

Создание и дублирование обновляют только новый компонент или новый `.d` и
индекс его модели, без пересканирования Gothic и архивов. Копия компонента
независима от оригинала: пользовательские файлы копируются,
а ссылка `visual` на общую модель сохраняется без копирования модели и текстур;
снимки функций и констант не вычисляются повторно. Иерархия вставляет новую строку
в уже открытую категорию, обычное редактирование обновляет существующую строку.
При выборе выделение меняется только у предыдущей и новой строки. Поиск скрывает
пустые категории и подкатегории, при отсутствии совпадений показывает сообщение.
Ctrl+D и Delete действуют при фокусе в иерархии, но не перехватывают ввод в полях.
В меню «Скачать» доступны модель 3DS и текстура. При нескольких текстурах открывается
выбор. TGA копируется без изменения, декодированную TEX можно сохранить как TGA
с альфа-каналом или скачать исходную TEX.

Проверенная `PropertiesSchema` кэшируется до изменения категории или одного из её
блоков. Форма повторно использует виджеты для той же схемы и режима редактирования,
когда схема показывает все поля и не содержит динамической секции неизвестных
свойств. При смене предмета сбрасываются черновики, ошибки и наблюдатели переменных,
затем заполняются новые значения; заполнение не запускает сохранение. Формы с
динамическим составом полей перестраиваются. Список визуальных эффектов кэшируется
до обновления проекта; значения эффектов самих предметов добавляются актуальными.
`IconImages.shared` хранит общий кэш изображений у корневого Tk, а не у каждой кнопки.

Панель ресурсов — проводник по `Assets/` проекта, независимый от выбранного предмета.
Слева дерево папок с ленивой загрузкой вложенных каталогов, справа содержимое текущей
папки; двойной клик по папке открывает её внутри панели. В подписях показываются
только имена. Переходы за пределы `Assets` через ссылки блокируются.
Используются `ScrollableArea` и универсальный `FileTile`: адаптивная сетка
на тёмном фоне, выделение, двойной клик и контекстное меню
для выбранного файла. Расширения `json` и `D` показываются в центре значка.
Необязательные иконки — `assets/icons/file.png` и `assets/icons/folder.png`.
Без иконки файла остаётся текст расширения, без иконки папки рисуется простой силуэт.
Изображения автоматически не создаются и не загружаются.

Контекстное меню ресурсов зависит от объекта: на пустом месте создаются папки и
пустые `.d`, файлы и папки можно дублировать и удалять с подтверждением.
Для папок доступны копирование относительного/абсолютного пути и переход внутрь,
для файлов — открытие в редакторе и системной папке. Ctrl+C/Ctrl+V копируют
выбранный ресурс в текущую папку; сочетания действуют только в проводнике.
`core/asset_files.py` выполняет операции внутри `Assets`, проверяет имена,
запрещает ссылки и копирование папки внутрь себя, подбирает свободное имя копии.
Корень `Assets` нельзя удалить или дублировать. Перед операциями приложение
сохраняет свойства, после обновляет репозиторий и иерархию.

Терминал сохраняет журнал сборки и добавляет строку ввода PowerShell. Ленивый
`core/powershell.py::PowerShellSession` запускает отдельный скрытый процесс
`pwsh` или `powershell`, начиная с папки проекта. Команды исполняются в одной сессии:
`cd`, переменные, `dir`, `start .` работают между вводами. Вывод читается фоновым
потоком через ограниченную очередь и дописывается пакетами в Tk. Есть история
Up/Down и остановка собственного дерева процессов; создание другой панели,
смена проекта и закрытие корректно управляют временем жизни сессии. Смена языка
сохраняет сессию. Это командная консоль с перенаправленным выводом; полноэкранные
интерактивные программы и запросы `Read-Host` не поддерживаются.

- Виджеты не записывают проект: `PropertyEntry`, `PropertyButton`, `ExpressionChoiceField` и `KeyValueList` отвечают за ввод и отображение.
- `ValueChoiceWindow` в `ui/windows/value_choice.py` строит окно выбора. Поле `ExpressionChoiceField` только открывает его и получает выбранное выражение.
- `PropertiesPanel` в `ui/panels/properties.py` строит панель из описаний полей. `PropertyEditor` в `ui/controllers/property_editor.py` проверяет изменения, вызывает сохранение и обновляет исходные значения формы.
- `SettingsFormRenderer` строит настройки, `ItemAppearanceController` управляет моделями предметов, `ToolRunner` выполняет команды в фоне. Они находятся в `ui/controllers/`; логика чтения, хранения и сборки остаётся в `core/`.
- `app.py` связывает панели и контроллеры. Старые плоские UI-модули удалены, импорты приложения и тестов используют новую структуру.

Схемы свойств загружаются только из `assets/properties/`: сначала рядом с исполняемым файлом, затем из каталога исходников. Файл категории в `categories/` содержит только `blocks` — упорядоченный список путей относительно `blocks/`. Для каждой конечной категории из `EDITABLE_CATEGORIES` загружается одноимённый JSON; группировочные узлы иерархии собственной формы не имеют.

`blocks/general/` содержит `main.json` (ID и названия), `parameters.json` (флаги и стоимость), `inventory.json` (массивы описания и автоматическая стоимость), `appearance.json` (модель и визуальный эффект). `blocks/potions/actions.json` содержит выбор функций действий и анимацию использования зелья; группа расположена после параметров. `definition.json` в папках `blocks/potions/` и `blocks/scrolls/` задаёт нумерацию, начальные игровые свойства, правила и `field_overrides` общих полей. Специальные блоки других категорий добавляются в собственные папки, когда появляются соответствующие схемы.

Остальные профили лежат в `blocks/weapon/`, `armor/`, `runes/`, `jewelry/`,
`food/`, `documents/`, `ammo/`, `misc/`. Оружие использует общий блок боевых
характеристик; броня и украшения — защиту. Общие требования и функции
надевания/снятия вынесены в `general/requirements.json` и `equipment.json`.
Руны используют `magic/spell.json` и общий `general/actions.json`.
Флаги новых подтипов оружия и украшений сохраняют их классификацию.
Новые категории используют существующее хранение `.d` и Copy-on-Write;
неизвестные поля импортированных предметов сохраняются.

Тип схемы `choice_list` задаёт одноколоночный список вариантов с `max_rows`.
Его расширение `action_list` добавляет параметры функций; оба хранят данные
в `editor_metadata` с `export: false`, используя общие кнопки и поля выбора.
У зелий `item_actions` допускает добавление до четырёх строк, новая строка — «Нет».
Старые сохранённые списки из пяти действий загружаются без потерь; добавить
строку сверх нового максимума нельзя. В `C_Item` объявлено `on_state[4]`
(индексы 0–3), однако список действий редактора выполняется внутри одного
обработчика `on_state[0]` у зелий. Четыре действия — ограничение интерфейса, а не
числа вызовов внутри Daedalus-функции.
`GroupedChoiceWindow` размером 480×320 показывает поиск и группы: пользовательские
функции из Scripts проекта, затем стандартные из Content игры.

`core/item_actions.py` разбирает реальные определения `func void` с аргументами
`int`, `float`, `string`. Имена без метаданных берутся из сигнатуры. Комментарии
не меняют синтаксис Daedalus; пока используется только `NAME` из `@INFO`:

```text
// @INFO NAME=Добавить опыт
// @PARAM VALUE=exp NAME="Кол-во опыта"
func void AddExperience(var int exp) { B_GivePlayerXP(exp); };
```

`VALUE` должен совпадать с именем аргумента, его тип берётся из функции.
Также поддерживается сокращение `// @PARAM exp="Кол-во опыта"`;
для аргумента с именем `VALUE` это `// @PARAM VALUE="Кол-во опыта"`.
В группе «Параметры» `FunctionActionList` создаёт поля
`[Добавить опыт] Кол-во опыта`. Значения независимы для каждой строки;
параметры добавляются и удаляются при изменении выбора. Каталог кэшируется
до обновления проекта. Назначения сохраняются в строке JSON вида
`[{"id":"project:Assets/Scripts/Actions/Experience.d#AddExperience","values":{"exp":"100"}}]`
в `editor_metadata.item_actions`; автосохранение, копирование предметов и XLSX
сохраняют этот формат. Старые строки с выбором файла читаются: однозначный файл
с одной подходящей функцией определяется автоматически, иначе требуется перевыбор.

`core/action_build.py` проверяет наличие функций, соответствие сигнатур и типы
значений. Выбранные пользовательские файлы вне Content включаются во временную
сборку один раз, с проверкой конфликтов. Для каждого предмета генерируется
`GE_ItemActions_<INSTANCE>` с обычными вызовами функций и аргументами в порядке строк;
`potion_build` назначает его в `on_state[0]` зелья только в сгенерированном INSTANCE;
свитки вызывают его через магический каст.
Ручной обработчик сохраняется первым вызовом, если это существующая void-функция
без аргументов; неподдерживаемое выражение вызывает понятную ошибку сборки.
Без назначенных действий поведение предмета сохраняется. Исходники игры и
назначенные `.d` не переписываются, копий функций для каждого предмета нет.
Новые встроенные действия не создаются.

`property_blocks.load_property_data` объединяет разделы, списки вариантов и начальные значения; затем применяет `field_overrides` по ключу существующего поля. Дубли блоков, настроек, разделов и полей, неизвестные переопределения и выход за пределы папки блоков отклоняются. Блоки берутся из того же набора ресурсов, что и категория. `PropertiesSchema` проверяет итоговую плоскую схему; виджеты работают с ней как прежде. Старый плоский формат остаётся читаемым для совместимости, но встроенные категории используют только блоки. Значения по умолчанию применяются при создании, не при открытии импортированного предмета.

Поля модели и эффекта находятся в одной группе «Внешний вид». В неё же помещаются существующие кнопки модели: для зелий доступны прежние операции ресурсов, для свитков — выбор существующей модели. Поле `resource` показывает имя без кавычек и сохраняет строковое выражение Daedalus. Оба вида предметов поддерживают выбор функций действий и их параметры; схема свитков использует `general/actions.json`.

## Как устроен проект мода

- В корне проекта находится `project.json` с названием и настройками.
- `Assets/Scripts/Content/` — проектные Daedalus-скрипты.
- `Assets/Items/Potions/<INSTANCE>/` — компонентные зелья. Для каждого используются `item.json` (данные предмета и шаблон), `params.json` (переменные/константы), `functions.json` (сведения о связанных функциях), `functions.d` (собственный код). Модели хранятся отдельно и назначаются через `visual`.
- Свитки сохраняются существующим механизмом Daedalus-файлов в `Assets/Scripts/Content/`: новые — в `Items/GE_Generated/`, импортированные — как проектные переопределения. Общая схема задаёт поля и начальные значения, а не меняет способ хранения. Новые свитки и их копии используют префикс `ItSc_`; редактирование ID сохраняет остальные `INSTANCE` и функции файла. Специфические игровые эффекты/заклинания не добавляются.

Редакторские метаданные скриптовых предметов хранятся внутри соответствующего
`INSTANCE` в строке `// @GE_METADATA {…}`. `scripts.parse_items` читает их,
`with_item_metadata` и `write_modified_item` сохраняют, не затрагивая соседние
предметы и функции. JSON записывается с ASCII-экранированием для совместимости
с CP1251. Дублирование и переименование сохраняют назначения, XLSX использует
прежний `@metadata` для свитков так же, как для зелий.

`potion_build.apply_potions` также обрабатывает действия проектных свитков и рун,
в том числе в проекте без зелий. `core/scroll_cast.py` сохраняет магическую
категорию и запускает `GE_ItemActions_<INSTANCE>` при касте через `Spell_Cast`.
Чтение документа и `on_state[0]` для активации свитка не используются.
Все свитки с назначенными действиями получают отдельные свободные `SPL_Reserved`:
проверяются ссылки на константы, уже назначенные ID и незанятые позиции
`spellFxInstanceNames`/`spellFxAniLetters`. Свободный слот связывается с
`Spell_GE_ItemActions`, используется существующая анимация `LGT`, а
`Spell_ProcessMana` проверяет обычную стоимость `SPL_Cost_Scroll`.
Диспетчер выбирает такой свиток по активному ID заклинания, без зависимости
от возврата `Npc_GetReadiedWeapon` для магии. Если свободных слотов недостаточно,
сборка останавливается, не заменяя чужие заклинания.

Назначенные действия заменяют исходное заклинание в сборке, а не дополняют его:
например, скопированный свиток огненного дождя с действием выдачи предметов больше
не вызывает дождь. Исходный `spell` сохраняется в проекте и снова используется,
если убрать назначенные действия. Оригинальные `Spell_Cast_*` не изменяются.
Добавляется `ITEM_MULTI`, чтобы применялось обычное поведение расходуемого свитка.
Для рун `ITEM_MULTI` не добавляется, круг магии сохраняется: руна остаётся
многоразовой. Действия запускаются только в `Spell_Cast_GE_ItemActions`, а не
при выборе/экипировке руны. Руны и свитки используют общий пул свободных ID;
для назначенных действий пока применяется стоимость маны `SPL_Cost_Scroll`.
Все изменения выполняются только в сборочной копии. Исходные `.d`, старые
`on_state[0]`, предметы и свитки без назначенных действий остаются неизменными.

`compiler_sources.prepare_compiler_sources` перекодирует UTF-8 `.d` (включая BOM)
в Windows-1251 только во временной папке. Установленный GDC читает и пишет ANSI
через Windows-1250, поэтому без BOM важно передавать именно игровые байты CP1251:
они сохраняются в DAT. Передача UTF-8 без такого преобразования даёт «Р…» вместо
русских названий; UTF-8 с BOM при записи DAT может терять кириллицу. Исходники
проекта сохраняют свою кодировку, существующие ANSI-файлы не перекодируются.
Непредставимые в CP1251 символы вызывают понятную ошибку с путём скрипта.
- `Assets/Models/<ModelName>/model.3ds` и соседние `.tga`/`.tex` — общая модель проекта. Её могут использовать несколько предметов без копирования ресурсов.
- `dist/` — готовые `.mod` и `.ini` (при включённой настройке возможно сохранение `Gothic.dat`).
- `logs/` — журналы сборки и операций.

## Основные правила работы

`core/model_library.py` индексирует общие модели. Файл `ModelName/model.3ds`
доступен в Daedalus как `ModelName.3ds`; имя не зависит от ID предмета.
Выбор модели показывает только библиотеку `Assets/Models` и стандартные модели
из Meshes/VDF установленной Gothic. Импорт создаёт новую папку библиотеки;
назначение существующей модели меняет только `visual`. «Снять модель» очищает
назначение, сохраняя общий ресурс для остальных предметов. Добавление текстур
изменяет общую модель, с резервной копией прежней папки.

При открытии проекта прежние `assets/model.3ds` предметов и плоские модели
из `Assets/Models` переносятся в папки библиотеки с резервными копиями в `backups`.
Ссылки прежних собственных моделей сохраняют имена `model_<INSTANCE>.3ds`;
переименование предмета больше не меняет имя общей модели. Неизвестные поля
и посторонние файлы предмета сохраняются. Папки данных `Assets/Items` и
исходников `Assets/Scripts` не упаковываются как ресурсы MOD.
Папка пользовательских `Scripts/Content` необязательна: если её нет, сборка
использует оригинальные скрипты и сгенерированные компоненты. При выборе старого
или нового пути приоритет имеет существующая папка `Content`, а не просто `Scripts`.
Компиляция по-прежнему идёт во временной папке вне `Assets`; исходники проекта
не служат рабочим каталогом компилятора.

При упаковке `BuildAssetService` использует имя папки для имени модели и
добавляет имя папки к именам её текстур. Ссылки материалов меняются только
в байтовой копии модели для MOD. Поэтому разные папки могут содержать
одинаковые `model.3ds` и `texture.tga`, не конфликтуя в Gothic.
Для старых моделей внутри предметов применяется тот же механизм уникальных имён.
Оставшиеся после переноса папки предметов только с текстурами не упаковываются:
необходимые файлы уже входят в общую модель. Эти остатки автоматически не удаляются.

`core/mesh_cache.py` сбрасывает устаревшую геометрию при установке и перед запуском
уже установленного мода. Список берётся из проверенного MOD: только исходные `.3ds`
задают одноимённые `.mrm`/`.msh` в `_work/Data/Meshes/_compiled` игры.
Сравнение имён не зависит от регистра. Каждый сбрасываемый файл сохраняется в
`backups/mesh-cache-<id>/` проекта с исходным относительным путём; действия видны
в `sync.log` и `launch.log`. При установке резервирование и удаление кэша входят
в общую транзакцию MOD/INI/квитанции и откатываются при ошибке. Посторонняя
геометрия, анимации, текстуры и архивы игры не затрагиваются. Одна лишь компиляция
проекта не меняет кэш игры. Gothic создаёт геометрию заново при следующей загрузке.

1. **Исходники Gothic 2 — только для чтения.** Изменения хранятся в отдельном проекте; во время сборки формируется временная копия игровых скриптов.
2. **Приоритет у проекта.** При совпадении `INSTANCE` проектная версия подменяет оригинальную. В иерархии есть режимы «Только проект» и «Проект поверх оригинала»; они влияют на отображение, а не на сборку.
3. **Зелье — отдельный компонент.** Импортированный оригинальный предмет сохраняет его шаблон и неизвестные свойства. Изменения не должны уничтожать другие `INSTANCE` или общие функции в том же `.d`-файле.
4. **Свойства редактируются по JSON-схеме.** Поля Daedalus хранятся как выражения; для нового зелья применяются значения по умолчанию, например `ITEM_KAT_POTIONS`, `MAT_GLAS`, `POTIONFAST`.
5. **Сборка:** подготовка временных исходников → объединение скриптов и компонентов зелий → компиляция `Gothic.dat` → упаковка вместе с ресурсами в `.mod` → создание и проверка `.ini` → публикация в `dist/`.
6. **Команды независимы:** «Компилировать проект», «Синхронизировать проект», «Запустить мод». «Собрать и запустить» выполняет их последовательно и прекращает работу при ошибке.
7. **Установка обновляет файлы мода:** `.mod` в `Data/ModVDF/` и `.ini` в `System/`; оригинальный `Gothic.dat` не заменяется. Для `.3ds`, поставляемых текущим MOD, сбрасываются одноимённые файлы кэша геометрии.
8. **Все конечные категории редактируемы.** `EDITABLE_CATEGORIES` в `core/categories.py` задаёт доступность команд интерфейса и загрузку JSON-форм. Оригинальные игровые предметы доступны только для чтения до копирования в проект. Создание, дублирование, переименование, удаление и XLSX используют существующие механизмы репозитория.

Это описание **текущего состояния архива**, а не список будущих возможностей. Новые виды предметов, редактор эффектов и пользовательских команд пока не считаются готовыми функциями.

## Приветственный экран

Между верхней панелью с заголовком и строкой поиска оставлен отступ 25 пикселей.

В Windows после отображения безрамочное стартовое окно получает `WS_EX_APPWINDOW` вместо `WS_EX_TOOLWINDOW`, чтобы оставаться доступным через панель задач. При показе окно поднимается и получает фокус, но не закрепляется поверх других приложений. Кнопка закрытия и Alt+F4 вызывают общий обработчик завершения редактора.

Приветственное окно размером 720×480 открывается по центру экрана без системной рамки и меню, с собственной кнопкой закрытия справа вверху. Слева от закрытия находится переключатель полного экрана и возврата к прежнему размеру и положению. При открытии проекта возвращаются меню, системная рамка, размеры и обычный режим редактора. Справа от поиска находятся квадратные кнопки-иконки «Создать проект» и «Открыть проект», высотой 40 пикселей наравне со строкой поиска. Иконка поиска имеет высоту 36 пикселей (90% высоты поля) и выровнена по центру вертикально. Каждая строка недавнего проекта содержит текстовую плитку с инициалами, название и полный путь; при наведении отображается курсор-указатель. При наведении доступная строка немного затемняется, а кнопки действий плавно появляются; таймеры анимации отменяются при уничтожении строки. Одиночный клик по доступному проекту или Enter открывает тёмный модальный диалог подтверждения; только подтверждение вызывает существующий обработчик открытия.

Доступность каталога проверяется перед отображением и открытием. Недоступные проекты имеют приглушённый перечёркнутый заголовок и не открываются. При наведении на такую строку появляется только кнопка удаления в крайнем правом столбце, без затемнения и анимации; она убирает запись из недавних без подтверждения. Для доступных проектов удаление записи требует подтверждения в тёмном модальном диалоге. Открытие и удаление используют общий `ProjectConfirmationDialog`. Обе операции с историей обновляют меню «Недавнее»; файлы проекта не затрагиваются. Создание и открытие используют существующие обработчики приложения, история хранится в прежнем `recent_projects.json`.

Локальные Canvas-компоненты в `ui/widgets/` реализуют узкую тёмную полосу прокрутки со скруглённым ползунком и скруглённые кнопки действий 40×40 с иконкой 20×20 и полями по 10 пикселей. Кнопки закрытия и полного экрана имеют размер 30×30 с иконкой 20×20 и полями по 5 пикселей. Окно перемещается удержанием левой кнопки мыши за заголовок и свободную область верхней панели в обычном режиме. Фон иконки компонуется с фактическим фоном кнопки. `IconImages` повторно использует прочитанную альфу исходного PNG при анимации; остальные окна используют прежние компоненты и стили.

Экран использует `IconImages` и проверяет наличие каждого PNG перед загрузкой. При отсутствии или ошибке чтения изображения показывается текстовое обозначение. Ожидаемые файлы: `assets/icons/search.png`, `create_project.png`, `open_project.png`, `open_folder.png`, `remove_recent.png`, `close.png`, `fullscreen.png`, `restore.png` (все в `assets/icons/`). Значки с инициалами отображаются текстом и файлов не требуют. Новые изображения не создаются и не скачиваются.

## Импорт и экспорт XLSX

В меню «Проект → Импорт → xlsx» и «Проект → Экспорт → xlsx» открывается
`SpreadsheetWindow`, использующее общий `EditorDialog`, формы, кнопки и тёмный
`ProgressBar`. Выбор пути выполняется системным файловым диалогом. До открытия
сохраняется текущий черновик; операции выполняются в отдельном потоке через
`SpreadsheetTask`, прогресс передаётся в Tk через очередь с одним актуальным
сообщением. Во время операции модальное окно блокирует правки проекта и закрытие;
после завершения показывает число предметов и затраченное время. После импорта
перечитывается выбранный предмет и обновляется иерархия.

XLSX создаётся стандартными `zipfile` и `xml.etree.ElementTree`, без зависимостей
и без установленного Excel. Структура соответствует
[SpreadsheetML](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/structure-of-a-spreadsheetml-document).
Первый лист — «Предметы»: колонка «Код» содержит INSTANCE, «Категория» — ключ
категории, затем идут отдельные колонки `name`, `description`, `value`, массивы
`text[0]`/`count[0]` и все остальные фактически присутствующие поля. Экспортируются
предметы проекта. Значения сохраняются как выражения Daedalus: строковые литералы
остаются в кавычках, константы и формулы Daedalus сохраняются без вычисления.
`@metadata` содержит JSON строковых метаданных редактора. Файлы моделей, текстур и
пользовательских функций не переносятся через XLSX; существующие файлы сохраняются.
Колонки можно переставлять, удалённая колонка и пустая ячейка не меняют свойство;
для пустой строки используйте `""`. Формулы самого Excel перед импортом нужно
заменить значениями. Чтение поддерживает inline/shared strings, числовые и
разреженные ячейки, связи листов Excel. Экспорт атомарен: ошибка не повреждает
предыдущий XLSX; строки, похожие на формулы, записываются как текст.

`ItemSpreadsheetService` сопоставляет INSTANCE без учёта регистра. «С заменой»
добавляет отсутствующие и обновляет существующие; «Только недостающее» добавляет
только отсутствующие коды; «Обновление» меняет только существующие. Существующими
считаются и видимые игровые оригиналы: изменения создаются через проектные
переопределения, оригиналы не записываются. Ограничение редактируемых категорий
сохраняется: readonly-строки пропускаются с отдельным счётчиком. Категорию
существующего предмета менять нельзя. Проверка заголовков, повторяющихся кодов,
значений и кодировки проходит до записи всего пакета. Изменения используют
`ProjectRepository.edit` и `create_item_from_fields` с существующими механизмами
компонентов и `.d`; неизвестные поля, соседние INSTANCE и функции не удаляются.
Новые предметы получают начальные значения из действующей схемы категории.
Перед записью затрагиваемые файлы копируются в `backups/xlsx-import-<id>/`;
при ошибке пакет откатывается, созданные предметы удаляются, репозиторий обновляется.

## Поля зелий и строки инвентаря

Для `scemeName` допустимы только «Выпить» (`"POTION"`) и «Выпить быстро» (`"POTIONFAST"`), в таком порядке. Источник `item_schemes` предоставляет окончательный список из `core/potion_schemes.py` и не дополняется значениями из предметов или дополнительными вариантами схемы. Новые зелья получают `"POTIONFAST"`. При импорте неизвестное явно заданное значение заменяется первым вариантом `"POTION"`; если поля в оригинале нет, оно не добавляется. Нормализация меняет только данные импортируемого компонента, исходный скрипт и прочие свойства остаются прежними. Уже сохранённые проекты автоматически не мигрируют.

Панель «Свойства» показывает INSTANCE подписью под заголовком, затем центральную разделительную линию шириной 90% с отступами 10 пикселей сверху и 20 снизу. Группы используют `PropertySectionFrame`: заголовок с линиями по сторонам вместо рамки, отступы по 10 пикселей и промежуток между группами 30 пикселей. Сворачивание групп сохраняется. Подписи происхождения, общие инструкции о кавычках и примечание о шести строках не отображаются.

Необязательное строковое свойство `tooltip` в описании поля или колонки включает `FieldLabel`: справа от подписи появляется вопросительный знак в круге высотой с текст. Подсказка появляется только при наведении на этот знак; само поле и подпись её не показывают. Без `tooltip` значка нет; `description` и `placeholder` не превращаются во всплывающие подсказки. В узком списке пар значений подсказки колонок объединяются у общей подписи. Текст подсказки не экспортируется в Daedalus.

Поля проектных предметов сохраняются через 1000 мс после последнего изменения,
включая ввод, вставку, выбор варианта и строки инвентаря. Фокус можно оставлять
в поле: Tk-переменные и `PropertyEditor.draft` хранят черновик в памяти отдельно
от сохранённого `Item`; несколько изменений записываются одной операцией.
Ctrl+S сохраняет немедленно, в том числе при русской раскладке Windows. Перед
переключением предмета/проекта, обновлением, закрытием и запуском инструментов
накопленные изменения сохраняются; ошибка останавливает переход и не теряет ввод.
Индикатор показывает изменения, запись или сохранённое состояние. Проверка
обязательных полей, ID и выражений показывает ошибки у поля без модального окна;
ошибка диска сохраняет черновик для повторной попытки. Таймеры и наблюдатели
снимаются при смене формы и её уничтожении. Исходные неизвестные выражения
не переписываются при открытии. Оригиналы игры и неподдерживаемые категории readonly.

`ProjectRepository.edit` после обычной записи обновляет только изменённый
компонент либо повторно разбирает его `.d`-файл; игровые скрипты, архивы и модели
не пересканируются. `PotionComponents.read_item` читает один компонент.
Списки репозитория обновляются в памяти с прежним приоритетом проекта; при
переименовании поддерживается индекс собственной модели. Иерархия обновляет
существующую строку и привязанный объект, сохраняя виджеты и прокрутку; изменение
ID, категории или попадания в фильтр требует перестройки раздела. Полное
сканирование остаётся для открытия/явного обновления проекта и структурных операций.

`PropertyEntry` сохраняет стандартные операции Tk Entry (выделение, буфер обмена, фокус), размещая поле на тёмной поверхности высотой 40 пикселей со скруглением 2 пикселя и отступами. Тип схемы `combobox` отображается совместимым `ExpressionChoiceField`, который открывает дочернее окно 480×320 по центру редактора с тёмным оформлением. Варианты имеют высоту 40 пикселей; «Выбрать» или Enter применяет выделение, Escape, «Отмена» и закрытие окна отменяют выбор. Окно не захватывает мышь и не блокирует другие поля. При повторном обращении поднимается существующее окно; при уничтожении поля оно закрывается. Принятый выбор сохраняется общим таймером после паузы, без требования потери фокуса.

Нативное поле и кнопка «…» встроены в Canvas через `create_window`, чтобы фон не перекрывал интерактивные элементы. Нажатие на текст или внутренние отступы фокусирует поле; окно выбора открывается по клику на текст, фон или «…».

Выбранный вариант в окне выбора имеет постоянный синий фон и акцентную обводку. Состояние выбора хранится отдельно от наведения мыши, поэтому выделение не исчезает после ухода курсора; при открытии отмечается текущее значение поля.

`PropertyButton` задаёт общий стиль и эффекты наведения кнопок моделей, вариантов списков и действий инвентаря. Удаление строки инвентаря использует `assets/icons/detele.png`, добавление — `assets/icons/create.png`; оба действия квадратные, высотой 40 пикселей, с отступами по 10 пикселей вокруг иконки. Удаление выровнено справа по нижнему краю полей, добавление находится под ним справа. На узкой панели поля строки располагаются вертикально. Изображения проверяются перед загрузкой; при отсутствии файла остаётся текстовый символ. Изображения не создаются и не скачиваются.

Подписи колонок `key_value_list` отображаются один раз над всеми строками; на узкой панели используется общая подпись с названиями через «/». Для тонкой иконки `create.png` при уменьшении включена нормализация альфы в `IconImages`, чтобы сохранить контраст; исходный PNG и отображение остальных иконок не меняются.

Основные поля — `instance`, `name`, `description`, `flags`, `value`. Скрытые `mainflag=ITEM_KAT_POTIONS` и `material=MAT_GLAS` задаются при создании; существующие импортированные выражения не перезаписываются. Выбор модели `visual` остаётся в панели ресурсов. Поле `effect` предлагает «Нет» (`""`) и доступные эффекты; `scemeName` в группе «Действия» выбирает анимацию использования. Неизвестное сохранённое значение списка отображается без изменений. Назначенные функции действий вызываются через сгенерированный обработчик `on_state[0]`; собственные игровые эффекты редактор не добавляет.

Тип поля JSON-схемы `key_value_list` задаёт `max_rows` (ёмкость массивов), `start_index` и два описания в `columns`: `variable` (имя массива), `label`, `type` (`string` или `expression`). Необязательный `reserved` сопоставляет имена массивов с выражениями автоматических строк: такие индексы исключаются из редактирования и добавления. Сам ключ поля списка в Daedalus не экспортируется; сохраняются обычные выражения `variable[index]` в `item.json` через существующий механизм компонентов.

У зелий используются `text[]` и `count[]`, индексы 0–5. Новые зелья получают `text[5]=NAME_Value`, `count[5]=value`, поэтому доступны пять пользовательских строк. При импорте автоматическая стоимость остаётся на исходном индексе; отсутствующие строки не добавляются автоматически. Разреженные индексы, константы, неизвестные поля и массивы вне диапазона сохраняются. Удаление строки убирает оба присваивания; добавление занимает свободный индекс. В широком интерфейсе столбцы имеют пропорцию 3:1, в узком располагаются вертикально.

Перед сохранением список проверяет поля `expression` на обычный текст и разделители операторов: например, `count[1]=2 минуты` отклоняется с указанием поля. В `COUNT[]` задают число или выражение, а единицы измерения помещают в `TEXT[]`. Это предварительная проверка; полную проверку синтаксиса и типов выполняет компилятор Daedalus.

Новые проекты создают `Assets/Items/Potions`, `Assets/Models` и `Assets/Scripts/Content/Items`.
Загрузка, сохранение, поиск эффектов и сборка используют эти пути. Для проектов,
которые ещё не перенесены, поддерживается прежнее расположение `Items` и `Scripts`
при отсутствии соответствующей папки в `Assets`; файлы автоматически не перемещаются.

## Рецепты

Левая панель рецептов использует общий `CategoryRow` с иерархией предметов:
поиск по коду/названию рецепта и названию категории, разделитель с вертикальными
отступами 15 px, раскрываемые категории только с проектными рецептами.
Между категориями задан отступ 25 px, перед первой категорией отступа нет.
Состояние раскрытия и прокрутка сохраняются при обновлении. У каждой категории
есть «+»: модальный выбор «Выбрать из Gothic»/«Создать новый». Создание сразу
назначает категорию. Между двумя разделителями расположен заголовок «Категории»
с кнопкой «+», открывающей модальное окно кода и названия. ПКМ по категории:
изменить, дублировать, удалить с подтверждением. ПКМ по рецепту: дублировать,
удалить с подтверждением. Копии сохраняют название и получают `<code>_copy`,
при конфликте добавляется числовой суффикс.
Рецепты без категории сохраняются в отдельной группе главного меню.

`core/game_recipes.py` читает обычные рецепты из игрового `Potion_Alchemy.d`;
`ui/windows/recipe_add.py` показывает поиск по названию, коду и результату.
Выбор сохраняет независимую JSON-копию с новым ID и выбранной категорией,
известную изначально (это явно указано в окне), без изменения игровых рецептов.
Учитывается мензурка, удерживаемая столом. Нестандартные обработчики с выражениями,
дополнительными эффектами или несовпадающими проверками/расходом не копируются;
окно показывает число пропущенных рецептов. Произвольный Daedalus не исполняется.

Категории алхимии задаются в `Assets/Recipes/categories.json` через
`core/recipe_categories.py`. Штатные коды health/mana/special/booze/tabak
привязаны к реальным подменю Gothic, названия можно менять. Пользовательские
категории генерируются как C_Info с Info_AddChoice и возвратом через
Info_ClearChoices. Пустые пользовательские категории в игре не показываются.
Изменение кода категории транзакционно обновляет привязки её рецептов через
`publish_files`; сбой записи восстанавливает прежние файлы. При удалении
категории её проектные рецепты сохраняются без категории, о чём предупреждает
подтверждение. Поле `binding` сохраняет штатное подменю Gothic при смене кода;
копия категории получает `binding: null` и становится самостоятельным подменю.
Удаление категории из редактора не удаляет оригинальные рецепты Gothic. Поле `category`
рецепта хранит код категории; отсутствие поля/пустая строка сохраняет прежнее
размещение в главном меню. Штатные рецепты сохраняются; переименование меняет
только description их категории во временной копии исходников.

`core/recipes.py` хранит алхимические рецепты версии 1 отдельными JSON в
`Assets/Recipes/Alchemy/<ID>.json`: `id`, `name`, `result`, `result_count`,
`ingredients` (строки `instance`/`count`) и `availability` (`type`: `always`
либо `global_variable`, во втором случае также `variable`). Запись атомарна;
проверяются пути, идентификаторы, регистр, количества, дубли и Windows-1251.
Повреждённый файл показывается в списке ошибкой и останавливает сборку.
Тип рецепта отделён каталогом Alchemy, чтобы позднее добавить другие ремёсла.

`ui/controllers/recipes.py` управляет черновиком, таймером автосохранения и
общим барьером `_save_editors` (Ctrl+S, переключения, сборка, закрытие).
`ui/panels/recipes.py` использует общие панели, группы и поля; поиск предметов
проекта/Gothic открывает `GroupedChoiceWindow`, сохраняется INSTANCE.
Есть создание, независимое дублирование и удаление с подтверждением. Ошибки
данных показываются у полей, ошибки диска — в статусе; ввод не теряется.
Просмотрщик в этом режиме скрыт, его место получает форма.

`core/recipe_build.py` вызывается из `ProjectTools._prepare` после объединения
предметов, NPC и включения проектных скриптов. Адаптер проверяет реальные
`POTIONALCHEMY_S1`, `PC_PotionAlchemy_End_Condition`, обработчик выхода и
`B_ENDPRODUCTIONDIALOG`; несовместимые исходники отклоняются. Новые C_Info
добавляют отдельные пункты основного меню стола, используя штатное условие
главного меню без требований навыков. Оригинальные рецепты не меняются.
Обработчик возвращает удерживаемую столом мензурку так же, как штатный выход,
затем проверяет ингредиенты и завершает взаимодействие штатной функцией.
INSTANCE возвращаемого предмета извлекается из исходного обработчика выхода,
INSTANCE результата и ингредиентов задаются пользователем.

Для каждого рецепта генерируется стабильная `GE_Recipe_<ID>_Craft(portions)`:
сначала проверяются положительное число порций, переполнение всех произведений,
знание и наличие всех ингредиентов; затем выполняются списание и выдача.
Диалог вызывает её с одной порцией. `batch_requirements` предоставляет расчёт
расхода и результата для нескольких порций на уровне данных.
Глобальные переменные знания проверяются как скалярные `var int`; отсутствующие
объявляются один раз с нулевым значением по умолчанию Daedalus.
Проверка символов и предметов учитывает подключённые Gothic.src исходники.
Генерируемый `GE_Recipes/Alchemy.d` включается последним, после зависимостей.
Все изменения выполняются во временном дереве сборки; JSON не пакуются в MOD.

`tests/test_recipes.py` проверяет формат, хранение, генерацию, конфликты и расчёт
порций; `test_recipe_ui.py` — форму, сохранение и блокирование переходов.
`test_recipe_game_build.py` включается переменными `GOTHIC_TEST_GAME` и
`GOTHIC_TEST_COMPILER`: компилирует тестовый MOD по установленным исходникам,
проверяет его содержимое и неизменность файлов игры. Эта проверка не запускает
Gothic: фактический расход, выдача, сообщения и анимация требуют проверки в игре.
